# 电竞工作室后台需求草案 v0.1

整理日期：2026-10-12

本文汇总本次沟通已确认的业务规则，作为第一版设计和后续开发的依据。标注“建议”或“待定”的内容尚未由用户最终确认。本文件是需求草案，尚未开始系统开发或部署。

## 一、建设范围

- 以《三角洲行动》业务为核心，管理获客、下单、派单、订单履约、人员、考勤、工资、提现、费用和经营数据。
- 管理后台优先，前端意向基础为 Art Design Pro：https://github.com/Daymychen/art-design-pro 。
- 打手端以后单独开发，后台提前设计共享数据和对接接口。打手端主要承担接单、上报完成、查看收入和申请提现。
- 上线安排已确定：后台与独立打手端均准备好后一起上线；开发安排仍先后台、打手端后续另做。
- 后台按正式对接流程设计，接单、完成上报及提现申请通过打手端发起。第一版不因过渡期独立使用而增加客服代上报等临时功能，正常的客服直接指派功能保留。
- 客户在日常业务中称“老板”；系统中称“客户”，与内部管理角色“老板”区分。客户不开放独立端，后台支持手动添加。
- 先完成核心流程，再按使用情况优化页面、字段、规则和报表。

## 二、菜单框架

| 板块 | 主要内容 |
| --- | --- |
| 数据概览 | 订单、收款、渠道和店铺业绩、打手费用、员工提成、费用支出、每日利润及待处理事项 |
| 快捷下单／派单大厅 | 选择预设订单项目、补充客户信息和打手可见备注、直接指派或发布到抢单池、查看待派和待接订单 |
| 订单管理 | 全部实际订单、状态、收款、负责人、队友、完成截图、取消及退单原因、退款及每单操作日志 |
| 游戏管理 | 游戏、订单项目／模板、客户价格、打手价格、规格、默认内容和所需信息 |
| 用户管理 | 员工、打手、客户分别管理；打手等级、状态和同时接单上限；账号及权限配置 |
| 人事考勤 | 个人排班、到岗、请假、缺勤、工时汇总 |
| 财务管理 | 订单验收与核查、收支对账、退款、打手结算、提现审核与发放、员工工资、费用报账、月度报表 |
| 操作日志 | 全模块日志汇总；也可从订单等具体记录查看相关日志 |

说明：订单管理和独立的人事考勤入口是沟通中提出的初版框架建议，最终菜单位置可在页面设计时调整。

## 三、角色与权限

| 角色 | 已明确的职责或权限 |
| --- | --- |
| 老板 | 内部管理角色，默认可查看工作室总利润和全员工资，其他模块及操作权限由权限方案配置 |
| 店长 | 可以查看整个工作室的人员和订单，默认可查看工作室总利润和全员工资 |
| 财务 | 工资方案和比例配置、订单验收、已完成订单退单及金额／打手报酬更正、退款审核或直接处理、提现审核与人工发放登记、费用录入与删除、经营及月度报表 |
| 人事 | 为每人设置上班时间和工时，人工登记到岗及出勤情况 |
| 运营 | 目前一人负责所有平台；可以创建订单；按指定参与平台中已完成订单的净流水计算运营提成 |
| 客服主管 | 暂时沿用客服同一套功能和权限，只查看本人业绩，不开放工资查看，无特殊主管流程 |
| 客服 | 可查看全部实际订单并按状态权限编辑、创建派单、解除接单并重新派单、填写原因后取消订单、确认收款、发起退款；已完成订单仍可修改备注，金额和打手报酬由财务修改；不能更改游戏管理中的订单模板及预设价格 |
| 打手 | 管理员手动建档、分配账号、设置等级和状态；每个账号可单独设置同时接单上限，以后通过独立打手端参与业务 |
| 超管／管理员 | 维护平台和订单来源、参与运营提成的平台、打手账号及等级规则；预留逐人权限开关 |

权限设计采用“角色默认权限＋个人开关”。模块可见性和查看、创建、编辑、审核等操作权限分别配置。其他人编辑订单，不改变原创建客服的提成归属。

默认数据查看范围：

- 工作室总利润和全员工资，仅老板、店长、财务可查看。
- 客服只查看本人业绩，不开放工资页面、工资明细或工资相关数据；客服主管暂沿用同样规则。
- 客服仍可查看全部实际订单。个人业绩的数据范围与订单查看范围分别控制。
- 运营、人事等其他员工默认仅查看本人工资和本人业绩，工作数据按原职责及权限配置开放。
- 财务正常计算客服底薪、提成和退款扣减，并纳入工资及经营报表。客服不查看工资，不影响计薪。
- 管理员可后续逐人调整查看权限；页面、明细、导出及数据接口遵守相同的查看范围。

已完成订单的金额和打手报酬仅由财务修改，客服仍可修改备注。其他字段沿用原权限配置，本次不额外增加限制。财务更正记录修改前后值、操作人和时间，并按既定规则更新受影响的利润、提成及报酬统计；金额更正与实际退款分别记录，真实退款继续走退款流程。

待定：超管、管理员与老板等角色如何对应，以及各角色最终的操作权限明细。运营已确认可创建订单，其余编辑权限仍通过权限方案确定。

## 四、客服岗位、平台与店铺来源

### 4.1 三个客服岗位

- 游戏大厅：在游戏大厅获客、拉订单。
- 小红书：发作品、看私信、报价，引流到微信或企微，再引导下单。
- 闲鱼：平台接单，随后发单。

客服岗位、订单获客来源、成交／沟通渠道分别记录。小红书引流到微信或企微成交的订单，仍按小红书来源归属统计。

### 4.2 来源可维护

- 订单来源由超管／管理员维护，客服下单时选择。
- 支持新增平台、店铺或来源项，新店开业后可直接添加。
- 订单来源平台与店铺分别记录，例如“订单来源：闲鱼；店铺：金盾电竞”，支持平台汇总和店铺明细。
- 当前仅闲鱼需要店铺选项，已有一家店铺“金盾电竞”；小红书、游戏大厅当前不显示或要求填写闲鱼店铺。
- 闲鱼店铺采用可维护的下拉选项，目前默认选择“金盾电竞”。超管／管理员可以随时新增店铺，新增后客服派单时直接选择，无需修改页面。
- 后续店铺名称确定后再添加；“待定”不作为一项实际店铺数据。
- 来源配置与维护操作全部留日志。
- 运营提成参与平台单独配置，目前仅开启闲鱼和小红书；以后新增平台可以选择加入。
- 参与平台由超管／管理员维护，提成比例由财务填写。

## 五、游戏管理与快捷下单

### 5.1 可选订单项目

游戏管理维护的是订单模板。每个模板成为快捷下单中的独立可选项，例如：

| 项目示例 | 客户订单金额 | 打手整单总报酬 |
| -------- | ------------ | -------------- |
| 70 788w  | 88 元        | 70 元          |
| 50 588w  | 待配置       | 50 元          |
| 娱乐单   | 待配置       | 待配置         |
| 趣味单   | 待配置       | 待配置         |

“w”用于哈夫币数量简称。娱乐单和趣味单可直接使用名称，无需填写哈夫币数量。

模板可配置名称、规格／目标、客户价格、打手价格、默认地图、默认备注和下单所需信息。未明确的价格由有权限的人员设置。

### 5.2 快捷操作

选择订单模板 → 自动带出默认价格和内容 → 补充客户及必要信息 → 选择指派或抢单 → 派单。

客服可以按订单状态权限编辑实际订单，但不能修改游戏管理的模板和预设价格；订单完成后，金额及打手报酬由财务修改，客服仍可修改备注。建议下单时保存模板当时的内容和价格，模板以后修改不覆盖历史订单。

### 5.3 发单信息

- 订单项目及客户金额、打手总报酬分别保存。
- 房间码与客户游戏 ID 二选一，至少填写一项。
- 地图可选具体地图或“不限”。
- 选择订单来源平台；来源为闲鱼时显示“闲鱼店铺”下拉，当前默认“金盾电竞”，以后可选管理员新增的店铺。
- 闲鱼记录平台订单号；建议按文本完整保存，避免长数字变化。
- 支持默认备注和临时补充，例如“结单提醒客户确认收货”。
- 建议每单另有系统内部订单号，关联平台订单号。

原发单格式中的“付款方式：金盾电竞”已确认实际表示店铺，后台正式字段命名为“闲鱼店铺”，示例为“闲鱼店铺：金盾电竞；订单来源：闲鱼”。

### 5.4 打手可见备注

- 第一版后台的派单页设置独立的“打手可见备注”填写区域，客服可填写和编辑，订单详情也可查看及修改。
- 订单已完成后，客服仍可修改备注，继续保留修改日志。
- 选择模板时可带出默认备注，客服可按实际订单补充内容；保存为该笔订单的备注，不修改模板原内容。
- 备注随订单保存，未来打手端在订单已向该打手开放展示时，接单前即可看到；查看仍遵守账号权限和等级开放时间。
- 本期后台完成备注录入、编辑、保存和对接字段准备；打手端的实际展示界面后续另做。
- 备注修改留日志，记录修改人、时间及修改前后内容。

## 六、收款规则

| 来源／类型 | 派单前要求 | 确认收款 | 付款凭证 |
| --- | --- | --- | --- |
| 大厅普通订单 | 客户已付款 | 客服手动确认 | 必须上传 |
| 大厅落地付 | 可先派单；打手接单后客户付款 | 客服手动确认 | 付款后必须上传 |
| 小红书等其他普通来源 | 客户已付款后派单 | 客服手动确认 | 必须上传 |
| 闲鱼 | 客户已付款后派单 | 客服手动确认 | 免上传付款截图，保留平台订单号核对 |

- 落地付目前仅限游戏大厅。
- 收款状态与订单履约状态分别记录。
- 收款确认记录操作者和时间。
- 收入按客户实际付款当天统计，不以订单完成或财务验收日期归属；闲鱼也按客户付款日期统计。
- 建议分别记录“客户付款时间”和“客服确认收款时间”，便于补录时仍按实际付款日期统计。
- 大厅落地付须确认收款且财务验收通过、订单已完成后，才计入创建客服的提成；大厅不参与运营提成。
- 闲鱼免传的是付款截图，结单完成截图仍然必传。

## 七、派单、等级与订单状态

### 7.1 两种派单方式

- 直接指定打手。
- 发布到抢单池，由有资格的打手抢单。

每单只对接一名接单负责人。订单通常由两名打手执行，但负责人也可以独自完成。

### 7.2 打手等级

- 高等级先看到订单，低等级延迟看到。
- 等级名称、数量和延迟时间由管理员设置，不在草案中写死。
- 建议以订单发布时间为起点逐级开放查看和抢单资格；后开放等级出现后，前面等级继续可抢。
- 该延迟机制用于公共抢单池；直接指派走指定负责人流程。
- 同一时刻，一笔订单只有一名有效接单负责人，每轮抢单只允许一人成功；客服解除接单后允许重新接单。

### 7.3 四个正常履约状态

| 状态   | 含义                                   |
| ------ | -------------------------------------- |
| 待接单 | 已发布，等待打手接单                   |
| 接单中 | 负责人已接单，正在执行                 |
| 待验收 | 负责人提交完成截图并上报，等待财务验收 |
| 已完成 | 财务验收通过，正式结单                 |

完成截图必传。负责人上报完成时选择独自完成，或选择一名队友。

财务验收不通过时：待验收 → 接单中。财务注明退回原因，由原负责人补图或处理问题后重新提交，订单再次进入待验收；重新提交仍须有完成截图。

每次提交材料、验收结果、退回原因和操作人及时间均保留记录。退回后仍由原负责人处理，只有财务验收通过才进入已完成并形成可提现报酬。

### 7.4 解除接单与重新派单

- 打手接单后临时无法继续，客服可以解除接单：接单中 → 待接单。
- 解除后清空当前负责人，保留历次接单记录；原负责人不能再对该单提交完成材料或选择队友。
- 客服可重新指定打手，或发布到抢单池；公共抢单继续遵守等级规则。
- 沿用原订单记录，保留客户、收款、价格及原创建人信息，改派操作不重复生成订单收入或成本。
- 日志记录操作者、时间、原负责人及状态变化，支持填写解除原因；重新派单和新负责人接单另记日志。

### 7.5 每个账号的同时接单上限

- 默认每个打手账号同时最多有 1 笔“接单中”订单。
- 负责人上报完成、订单进入“待验收”后，该单不再占用同时接单名额，可以继续接下一单。
- 后台可对每个打手账号单独设置同时接单上限；工作室使用的账号可单独调高，具体数量按账号配置，不写死。
- 上限按该账号作为当前有效负责人的、未取消的“接单中”订单数量计算。实际接单时由后台统一校验，防止同时抢多笔绕过上限。
- 用户管理中展示当前接单数量和上限，上限的修改权限纳入账号权限配置，修改操作留日志。
- 建议：财务验收退回时保留原负责人并允许退回，不因接单上限阻断验收处理；如退回后数量超过上限，则暂停接新单，直到数量低于上限。下调上限时同样保留现有订单，限制新增接单。该冲突处理方案属于待确认的设计建议。

### 7.6 取消订单（退单）

- 客户取消或订单最终无法继续时，客服可以取消订单。
- 客服可取消的状态为“待接单、接单中、待验收”；“已完成”订单如需退单，由财务处理。
- 取消时必须填写退单原因；未填写原因不能提交取消操作。
- 保留完整订单记录、取消前的履约状态、负责人及接单历史，不删除原订单。
- 操作日志记录取消人、时间、退单原因和取消前后变化。
- 取消后终止该单的继续派单、接单和完成上报，已取消订单不占同时接单名额。
- 建议在正常四个履约状态之外保存“已取消”终止标识及取消记录，页面具体展示方式在设计时确定。
- 取消与实际退款分开记录；需要退款的仍按财务退款流程处理，大厅仍不设置退款流程。
- 未接单取消时，整单打手报酬默认 0 元；已接单或待验收取消时，由财务按实际完成情况确认最终整单报酬。
- 已接单订单在财务确认报酬前标记为“报酬待确认”，保留约定成本，不先按 0 元冲销；财务确认后按最终报酬更新成本和利润。有客户付款记录的，回到原付款日更新。
- 财务确认的是整单最终报酬，仍按单人全拿、两人固定平分的规则分配，原金额、最终金额和调整记录留存。

客服不能撤销已完成订单的财务结算。解除接单后再取消、且已经有执行历史的订单，建议交由财务确认报酬，避免仅因当前显示待接单而直接归零。

## 八、打手报酬与提现

### 8.1 报酬分配

- 模板中的打手价格是整单总报酬。
- 经营利润统计中，客户付款当天即按该单约定的整单打手报酬计入成本；未验收时作为约定／预计成本展示，财务验收通过后才形成打手可提现报酬。
- 独自完成：全部归负责人。
- 选择一名队友：两人固定平分整单总报酬。
- 例：总报酬 70 元，独自完成拿 70 元；选择队友则各 35 元。
- 建议队友从后台已建档的打手中选择，便于对应结算账户。
- 退款时，财务根据实际情况确认打手最终总报酬，保留原金额、调整金额和原因。
- 取消订单时，未接单默认报酬为 0 元；已接单或待验收由财务根据实际完成情况确认最终整单报酬，分配规则仍为单人全拿、两人固定平分。
- 后续调整打手总报酬时，回到客户原付款日更新该单成本和经营利润，保留调整记录。

### 8.2 提现

正常结单：财务验收订单通过 → 报酬归入各打手可提现金额 → 打手申请提现 → 财务审核 → 财务统一人工转账 → 后台登记已发放。

取消补偿的设计建议：有报酬的取消订单由财务单独确认结算后，计入对应打手可提现金额，保留取消标识及补偿结算记录，不通过改成正常已完成订单来结算，避免误计客服或运营提成；具体操作入口在财务页面设计时确定。

- 客服／运营工资与打手可提现金额分别管理。
- 建议提现单状态为待审核、待发放、已发放、已驳回。
- 申请中的金额先占用，避免重复申请；驳回后恢复可申请额度。
- 财务手动转账，后台记录发放金额、时间、经办人，并支持上传转账凭证。
- 提现审核、付款和订单验收分别留记录。

待定：提现最低金额、频次或固定发放日、手续费、已付款后发生退款的冲抵办法，以及平分出现分币尾差时的规则。

## 九、员工工资与提成

### 9.1 工资方案

- 当前主要使用底薪＋提成。
- 预留纯提成、固定工资方案，由财务为员工选择和配置；支持按岗位应用。
- 底薪金额、提成比例先留空，标为“待配置”，上线后由财务填写；缺失配置不能直接按零结算。
- 工资方案记录生效时间和修改日志，已结算的历史工资保留原记录。
- 工资通常“压 15 天”发放，具体发薪日期后续设置。退款提成差额在退款当月工资结算中处理。
- 客服及运营提成计入财务验收通过、订单完成月份的工资，工资所属月与经营利润归属日分别记录。例如 10 月付款、11 月完成，提成计入 11 月工资，提成成本仍补计到 10 月原付款日。
- 预留按工时计薪开关，当前关闭。以后可以启用并设置时薪等参数。

### 9.2 客服提成

客服提成＝符合计提条件的已完成订单成交金额扣除累计退款后的剩余金额 × 财务配置的客服提成比例。

- 默认归创建订单的客服。
- 所有来源均须确认收款且财务验收通过、状态为“已完成”后才计入客服提成；未完成订单不计入正式提成。
- 客服提成计入订单完成月份的工资。
- 经营利润中的客服提成成本，在订单完成后补计到客户原付款日；退款后回到原付款日更新该单提成成本。
- 部分退款按剩余成交金额计算；全额退款不计提成。
- 例：88 元订单退款 20 元，以 68 元计算提成。
- 其他客服操作订单，提成仍归原创建客服。
- 客服主管暂沿用客服方案，个人工资配置由财务维护。
- 客服及客服主管的工资由财务正常核算，工资页面和明细不对其本人展示；本人可查看个人业绩。

### 9.3 运营工资

运营工资＝底薪＋各参与平台已完成订单的净流水提成。

- 目前只有一名运营负责所有平台。
- 当前参与平台仅为闲鱼、小红书；游戏大厅不参与。
- 每个平台分别配置提成比例。
- 仅计算参与平台中已确认收款、财务验收通过且状态为“已完成”的订单净流水，与哪个客服处理订单无关；未完成订单不计入正式提成。
- 运营提成计入订单完成月份的工资。
- 经营利润中的运营提成成本，在订单完成后补计到客户原付款日；退款后回到原付款日更新该单提成成本。
- 部分退款扣除退款金额后计算，全额退款不计。
- 运营可以创建订单；自己创建的订单只计算运营提成，不额外拿客服提成。
- 客服原有提成正常计算。
- 按平台保留明细，闲鱼另保留店铺明细，再汇总到运营工资明细；新增闲鱼店铺沿用闲鱼平台的运营提成规则。
- 后续平台可由超管／管理员添加并选择是否参与，比例由财务设置。

### 9.4 退款后的提成扣回

- 适用于闲鱼、小红书及后续平台的客服／运营提成；大厅订单不考虑退款。
- 退款产生的提成差额自动在退款当月工资结算中扣减，工资按“压 15 天”的安排发放。
- 对已完成并符合计提条件的订单，提成尚未发放时按退款后的净成交金额正常计算；已经按净额计算的部分不再额外扣一次。未完成订单尚未产生正式提成，不生成提成扣回项。
- 提成已经发放时，重算该单应得提成，仅将多发差额列入退款当月工资扣回项；扣回的是多发提成，不是客户退款总金额。
- 保留原工资发放记录，另记退款调整明细，关联订单、退款、员工、扣回金额及扣回月份。
- 重算使用该单原计提比例和归属；多次部分退款仅扣回新增差额，避免同一差额重复扣除。
- 新增平台支持退款，不代表自动参与运营提成，参与范围仍由管理员配置。
- 打手报酬及已提现金额不适用员工工资自动扣回规则，仍需另行确定。

现阶段按当月工资足够扣回提成差额处理，不设计工资不足或差额跨月顺延场景。

## 十、人事排班和考勤

- 人事可以设置每个人的上班时间和应工作时长，不要求所有员工班次相同。
- 预留班次可选项，支持个人独立排班和跨夜班次。
- 到岗记录由人事操作，客服无需手动打卡。
- 人事维护到岗、请假、缺勤等记录，系统汇总工时。
- 当前工时用于排班和考勤，不直接按工时计算工资。
- 以后按工时计薪的功能通过工资方案开关启用。

待定：迟到、请假、缺勤等是否影响底薪，以及相应计算规则；不默认制定扣款标准。

## 十一、退款、费用和经营报表

### 11.1 退款

- 大厅订单不考虑退款，不提供该来源的退款流程；闲鱼、小红书及后续平台支持整单退款和部分退款。
- 客服可以发起退款申请，由财务审核处理。
- 财务也可以直接操作退款。
- 退款关联原订单，记录金额、原因、经办人和时间。
- 退款可关联该单的取消记录；仅提交订单取消不代表实际退款已经完成。
- 退款按用户最后更正的规则，回到原付款日扣减收入，更新原付款日的净收入统计。
- 例如：昨天客户付款 88 元，今天实际退款 20 元，则昨天的净收入由 88 元改为 68 元；今天不因这笔退款扣减当天净收入。
- 原收款金额、实际退款金额、实际退款时间和操作日志仍保留，便于核对资金往来；统计归属日期与退款实际发生日期分别记录。
- 客服和运营提成按扣除累计退款后的金额调整；全退为零。
- 客服／运营退款提成差额在退款当月工资结算中自动扣减；已经按净额计算的不重复扣除，详见 9.4。
- 打手报酬由财务按实际情况确认调整。
- 调整前后内容全部留日志。

待定：打手已提现后出现退款，报酬差额如何追回、抵扣或记入后续调整。

### 11.2 费用报账——以最后确认规则为准

- 财务统一录入，提交后直接入账，无需审核。
- 记录费用类别、金额、发生日期、用途和凭证。
- 财务可以删除误录的报账记录。
- 删除后撤回该记录对费用和利润统计的影响，删除操作及原内容保留在日志中。
- 建议采用可恢复删除，减少误删后的恢复成本；恢复权限可由管理员配置。

注意：费用无需审核，不改变订单验收、客服退款申请和打手提现的财务审核流程。

### 11.3 利润口径

每日净收入（按原付款日归属）＝该日客户付款金额－归属于该日收款订单的累计退款金额。

每日利润草案＝每日净收入－当日归属的打手报酬－客服提成－运营提成－当日其他费用。

- 已确认：收入归属客户实际付款当天，不以订单完成、财务验收或平台结算日期代替。
- 已确认：客户付款当天，将该单约定的整单打手报酬计入成本，包括尚未验收的订单；报表区分约定／预计成本与最终确认报酬。
- 已确认：客服及运营提成须待订单财务验收通过、状态为“已完成”后才计提；完成后将提成成本补计到客户原付款日，运营提成仅计算配置参与的平台。未完成订单不计入正式提成成本。
- 已确认：客服及运营提成的工资所属月按订单完成月份记录，经营利润中的提成成本按客户原付款日归属，两者分别统计。
- 已确认：退款回到原付款日扣减，原付款日的日报净收入随退款更新；相关月度收入汇总同步更新。订单详情保留该单累计收款、累计退款和剩余净收入，以及实际退款时间。
- 已确认：退款引起的提成变化，以及财务后续调整打手报酬，均回到原付款日修正该单成本和利润，相关月报同步更新。
- 历史收入报表随退款更新；客服／运营退款提成差额在退款当月工资结算中处理，原工资发放记录保留。打手已提现后的报酬处理仍待确认。
- 报表中的提成成本调整与工资中的实际扣回分别记录，避免同一差额重复冲减成本。
- 每日利润不扣底薪。
- 底薪在月度报表中再扣除。
- 月报汇总时避免重复扣除已在日报计入的提成、打手费用和其他费用。
- 打手报酬成本与实际提现付款分别记录，避免同一笔成本因提现再次重复计算。

订单收入、打手成本、客服及运营提成的经营统计归属日为客户付款日；其中客服和运营提成只有在订单完成后才生成，并补计到原付款日。后续退款或报酬调整回改原付款日的经营统计。日报包含尚未验收订单的约定／预计打手成本，提成成本会随订单完成补计，利润随之更新，应清楚标识这一口径。建议提成比例未配置时，将相关成本和利润标为“待配置／统计未完整”，避免静默按零展示。

## 十二、日志与数据留痕

- 所有板块都有操作日志。
- 每笔订单有独立操作日志，同时汇总到全局日志。
- 至少记录操作人、时间、对象、动作，以及重要字段修改前后的内容。
- 覆盖下单、派单／抢单、解除接单、重新派单、订单取消及退单原因、改单及备注编辑、收款、上传凭证、队友选择、验收、退款、报酬调整、提现、工资配置、考勤、来源及等级配置、接单上限设置、费用新增和删除。
- 日志查看范围跟随账号权限，普通账号不能改写操作日志。
- 业务记录删除时，相关操作日志继续保留。

## 十三、独立打手端的接口准备

后台提前设计以下对接能力，打手端后续另做：

- 使用管理员建立的打手身份及等级、状态、同时接单上限。
- 按等级和开放时间获取可接订单。
- 订单向该账号开放展示时即可读取打手可见备注，接单前可查看。
- 抢单或接收指定订单时校验账号接单上限，确保同一时刻一单只有一名有效负责人，每轮抢单只有一人成功；解除后可重新接单。
- 查询本人订单、提交完成截图、选择队友。
- 查询本人报酬、可提现金额及提现进度，提交提现申请。
- 与后台共享订单、收款、验收和结算状态。

接口及数据校验需要同时遵守权限、等级、订单状态和金额规则。后台具体技术选型、接口字段和登录方案在开发设计阶段确定。

## 十四、后续补齐的事项

1. 打手已提现后的退款调整方式。
2. 取消补偿的结算入口及少数异常订单处理；接单上限与验收退回冲突的设计建议。
3. 角色及个人权限明细、具体发薪日期等上线配置。

其他细项可以作为后续配置或迭代项。提成比例、班次、等级等待时间等由指定人员上线配置，不需要现在一次填完。
