# 商家主账号与客服账号（已确认）

用户确认沿用总后台普通客服的日常订单流程，在商家归属内执行。商家仍使用独立登录通道与 merchant 角色，不能直接授予全站 support 角色。

- 每个商家一个主账号，多名客服。超管指定或交接主账号，旧主账号停用，历史归属不改。旧数据不自动猜测主账号。
- 商家主账号管理自己的客服：新增、改昵称、重置密码、启停、删除；客服不能管理其他账号。总后台保留统一管理，删除和主账号交接仅超管。
- 删除移除登录资格和在职名单，保留用户稳定 ID、订单创建人、操作人和审计记录，历史姓名标记“（已删除）”。删除后的登录名可复用，昵称可重复，新账号新 ID，旧会话不能复活。
- 同商家共享全部订单，按客服记录创建和操作责任；商家统一结算。主账号与客服都能查看客户价、结算价、商家总应付、已付和欠款。
- 客服负责发单、指定/改派打手、放回抢单池、退单交接、跟进、公开备注和未验收整单取消。已验收由总后台处理。取消留原因和日志，不新增支付、部分退款或改价流程。
- 保留现有商家字段和数据权限，不泄漏打手报酬、内部备注、全站用户或其他商家信息。不授予任何财务权限。
- 保留现有数据、账号和本次之前已完成的功能。开发、测试、构建在 D 盘隔离副本进行，不改变生产服务器、现有数据库或 COS 任务。

## 数据与接口

`Merchant.ownerUserId: string | null` 为主账号唯一来源。`Staff.merchantRole?: 'owner' | 'support'` 按归属计算，`Staff.deletedAt?: string | null` 为软删除标记。角色仍为 merchant。

`GET /merchant/staff -> {records: Staff[]}` 与 `POST /merchant/staff {id?,username?,name,status?,password?} -> Staff` 仅本商家主账号；后者严格限制字段。

`POST /merchant/staff/:id/delete -> Staff` 仅主账号删除本商家客服；`POST /users/:id/delete -> Staff` 仅超管删除商家客服；主账号不能直接删除。

`POST /merchants/:id/owner {userId} -> Merchant` 仅超管原子交接，停用旧主账号并撤销会话，启用新主账号。已有 `/users` 不得绕过这些约束。通用请求身份与幂等校验继续生效。
