## 1. 目标与范围

在现有项目中开发可正式使用的手机打手端，与管理后台共用账号、订单、财务数据和权限规则，完成接单、执行、提交、验收、提现的完整流程。

- 产品形态：手机网页（H5），使用现有 Vue 3 项目开发，适配安卓和苹果。支持添加到手机桌面，按浏览器能力提供网页推送。
- 用户主要在中国大陆；账号总量约 50～100，常态同时在线约 10 人。
- 账号由工作室在现有后台创建，打手使用账号、密码登录。首版不开放自行注册，不要求绑定微信或加入企业微信。
- 企业微信、普通微信自动消息对接已从首版范围移除，不作为开发或上线前提。不要继续围绕企业微信成员、应用权限等扩展需求。
- 沿用现有源码和业务后端，在原工程内增加手机布局与页面。保留原后台功能、组件和示例，不再嵌入另一套早期独立应用或另建互不相通的账本。
- 当前仅在电脑本地运行；尚未准备域名、服务器。现有业务数据均为测试数据。

## 3. 账号、权限与接单上限

### 3.1 账号来源

由后台管理员创建、维护打手账号。沿用现有登录会话、停用账号、密码重置、本人修改密码能力，不另建一套账号。

### 3.2 三个独立开关

后台现有 `playerAccess.login / claim / withdraw` 必须真正控制手机接口，不能只隐藏按钮。

| 后台设置 | 手机端行为 |
| --- | --- |
| 禁止登录或停用账号 | 禁止进入受保护业务；遵守现有会话撤销逻辑 |
| 禁止接单 | 禁止接新单，已有订单仍可提交完成 |
| 禁止提现 | 禁止新申请，不清除已有报酬或改写在途提现 |

### 3.3 同时接单数量

- 默认同时执行 **1 单**；后台可调整个人上限，直接使用现有配置。
- “接单中”占用名额；提交完成进入“待验收”后释放名额，可以接下一单。
- 申请退单但客服尚未批准时，仍为接单中，继续占用名额。
- 沿用后台现有验收退回处理：保留原负责人；若因退回使接单中数量暂时超过上限，允许处理已有任务，但禁止继续接新单，不强行丢弃旧任务。
- 最新后台的授权状态更正不受当前接单上限限制，因此也可能形成暂时超限；手机端应如实显示并禁止继续接新单，不撤销合法更正。正常打手接单仍严格遵守上限。

## 4. 接单、拒单、退单与订单状态

### 4.1 指定订单

正常派单时，后台指定打手后仍显示待接单，打手本人接受后才变为接单中。不要把“已指定”直接改成“已接受”。后台授权人员通过“更正订单状态”另行登记接单中，属于第 4.5 节的人工更正路径，应显示其真实来源。

- 指定订单只允许对应打手接受。
- 接受前允许拒绝，必须填写原因。
- 拒绝后交回客服重新分配，不自动取消客户订单，不自动放入公共抢单池。
- 指定后 **5 分钟仍未接受**，提醒客服处理；客服决定是否重新指派，不自动取消订单。

### 4.2 公共抢单池

沿用后台打手等级、开放延迟、接单开关和接单上限。多人同时抢同一单时，只能有一人成功，其余明确显示订单已被接取，并刷新状态。

### 4.3 已接订单申请退单

- 打手填写原因提出申请，由客服确认。
- 确认前保持接单中和当前负责人，不自行释放订单或名额。
- 客服批准后回到“待分配”，由客服选择重新指定打手或放回抢单大厅。
- 客服驳回后继续由原打手执行，并向打手展示处理结果及原因。
- 退单与客户退款是两个流程；退单不自动产生退款，也不自动结算补偿。需要补偿时沿用后台财务流程。
- 保留申请、处理人、处理时间、理由和原负责人历史；不允许重复申请、重复批准造成多次释放。

### 4.4 与现有状态模型的衔接

目前订单状态为 `pending / active / review / completed / canceled`，派单方式为 `pool / direct`。“待分配”是已确认的业务状态表现，但具体存储方式尚未指定。

新对话应按第 0.2 节统一共享改动，采用兼容的派单子状态或必要字段。关键是：拒单或退单批准后，订单应留在客服待办中，不能因为清空指定人就被公共池立即接走；不要只改前端标签。后台列表、筛选、统计、审计和数据检查须同步适配。

### 4.5 必须兼容后台免截图状态更正

这是左侧“后台端”已完成的最新规则，不能被手机开发恢复成旧的“后台待验收也必须截图”限制。

- 财务、店长、工作室老板、超管四类角色且具备 `orders.edit`，可通过 `correct-status` 在五种状态间更正，必须填写原因，无需完成截图。普通管理员和普通打手没有此权限。
- 执行、待验收、完成仍需要真实的打手负责人；历史停用打手可用于合法历史更正。完成仍须满足足额收款及原资金规则，不是任意绕过结算条件。
- 后台免图登记采用 `source:'status-correction'`、`correctedBy`、`correctionReason` 等现有字段；手机详情按本人可见范围显示“后台更正/后台登记”和必要说明，不伪装成打手上传材料。
- 后台更正为完成、取消、待验收或接单中后，手机任务、可操作按钮、余额及排行及时读取服务器最新结果。已经失效的退单或提交动作须由服务端拒绝并提示刷新。
- 同一条订单的财务更正、打手提交、退单处理竞争时，服务端检查最新状态，不允许晚到请求覆盖已生效状态。
- 取消、重开、完成回退和再次完成继续沿用原报酬恢复、结算快照、冲正及人工差额处理，不能因手机刷新或重复提交再结算一次。

## 5. 订单详情、完成材料与双人报酬

### 5.1 信息范围

- 接单前：可看项目、服务要求、打手报酬。
- 接单后：按本人参与关系展示必要的房间码、游戏 ID 等执行信息。
- 手机端不展示客户联系方式、客户实际付款金额、工作室利润、员工工资或他人的收款资料。
- 接口按接单前后及本人关联关系返回字段；不能将敏感数据全部返回后仅用 CSS 隐藏。订单备注、模板快照、历史记录和附件也要检查是否夹带敏感信息。

### 5.2 提交与验收

- 负责人上传完成截图并提交，订单进入待验收。
- 沿用现有材料要求：1～10 张图片，每张不超过 8 MB，PNG/JPEG/WebP，服务端检查真实格式及附件权限。
- 财务验收通过后，按后台规则结算报酬；提交完成本身不产生可提现收入。
- 验收退回后显示原因，允许负责人补充材料再次提交；保留历次材料及处理记录，不能重复结算。
- 上述截图要求针对打手本人正常上报。后台免截图登记是独立授权路径，手机端必须能读取这种没有图片的合法记录；不把它显示为数据损坏，也不自动补造上传历史。

### 5.3 双人订单

- 负责人在完成上报时选择实际参与的队友，由财务核对；首版不增加队友确认环节。
- 报酬平分；若总额有无法平分的 1 分钱，**多出的 1 分归负责人**。
- 例如总报酬 10.01 元：负责人 5.01 元、队友 5.00 元；两人合计必须等于订单报酬。
- 接单排行仅计负责人；队友自己实际收到的提现计入其提现排行。

**已发现的后台差异：** 当前源码在提交、结算及部分更正流程中仍会拒绝奇数分的双人报酬。新对话须将这项作为配套后端改动统一实现，更新分配算法及相关校验、冲正、退款核对、诊断和测试，不能只在手机页面修改显示。特别要覆盖最新后台免图更正路径。已结算历史继续遵守原快照与差额处理规则。

## 6. 钱包、押金和提现

### 6.1 钱包与财务调整

- 手机显示本人可提现余额、在途提现、已发放提现及可解释的收支明细，数值来自现有后端账本。
- 财务补款计入可用报酬；扣款只扣可用部分，超出部分登记待追回，由财务人工处理。
- 不动在途或已付款提现，不建立新的自动负余额，也不自动从未来收入追回人工差额。
- 已提现后发生客户退款或报酬减少，沿用“后台端”已确认的财务人工核对、登记处理结果流程。

### 6.2 独立押金

- 押金与报酬余额分开；打手可查看自己的押金余额和明细。
- 日常打手扣款走可用报酬，不走押金。押金退出处理仅用于退店或跑路，由财务登记。
- 押金不设置自动接单门槛；是否能接单由后台接单开关控制。
- 不把押金混入可提现报酬或提现排行榜。

### 6.3 提现规则（已确认）

| 项目 | 规则 |
| --- | --- |
| 手续费 | 首版为 0 |
| 最低门槛 | 不另设起提门槛；实际金额必须大于 0，最小 0.01 元，不能提交 0 元申请 |
| 金额上限 | 不超过当前可提现余额，申请成功即占用相应金额 |
| 每周次数 | 每人每自然周最多 7 次，按北京时间周一 00:00 至下周一 00:00 前计算 |
| 占用次数的状态 | 待审核、审核通过待发放、已发放 |
| 财务驳回 | 释放占用余额并返还次数，保留驳回原因与记录 |
| 打手撤回 | 仅待审核时可自行撤回；释放占用余额和次数，保留历史 |
| 审核通过后 | 打手不能自行撤回，后续由财务按原流程处理 |
| 支付方式 | 微信、支付宝收款码 |
| 审核与付款 | 财务人工审核、人工发放，登记真实付款凭证 |

收款资料由打手维护，提现时选择收款方式。**每笔申请保存当时的收款资料快照**，之后修改收款码只影响新申请，避免财务支付旧申请时收款对象被替换。

收款码及提现详情仅本人和有对应财务权限者可看。上传的收款码不是公开品牌图片，不应复用公开资源接口暴露。

### 6.4 次数及资金实现要点

以下是为已确认规则提供的实现约束，不是新增业务收费或审批环节：

- 次数绑定申请产生时所属的自然周，不按付款周计数；跨周审核不应挤占新周名额，跨周撤回不应让新周“剩余次数”超过 7。
- 服务端统一时间计算和校验，刷新网页、换手机、重启服务不能重置次数。
- 同时申请、多次点击、超时重试不能重复占余额或次数；提现创建、撤回、审核、付款须有事务及防重复处理。
- 撤回与财务审核竞争时，只允许一个有效结果；被撤回的申请不能继续通过或付款。
- 当前提现状态仅有 `pending / approved / paid / rejected`，新增撤回状态后，钱包计算、后台筛选、导出、诊断、审计及类型均要同步。
- “财务已登记发放”和“真实银行到账”应准确表述，接口成功本身不是外部支付到账证明。

## 7. 排行榜

### 7.1 接单排行

- 按服务端认定已有效完成并完成相应结算的订单统计，不按抢到过多少单或点击接单次数统计。正常路径为财务验收完成；合法的后台免图更正完成也属于有效完成，不能仅以“有截图”或“点击过验收按钮”作为筛选条件。
- 只计负责人，一单只计一次；队友不增加接单排行数量。
- 全额退款的订单不计入；部分退款仍计 1 单。退款以后台实际生效记录为准，未批准申请不提前扣排行。
- 取消、退单、被解除负责人以及未完成订单不作为有效完成单计入。

### 7.2 提现排行

- 按已由财务登记发放的提现金额统计；待审核、待发放、被驳回、已撤回均不计。
- 每笔发放只计一次，不将押金退还、钱包余额或申请金额混为已提现金额。
- 按真实发放时间归属统计月份。

### 7.3 展示与默认实现

- 登录后的打手可以看排行；展示昵称、头像及对应的订单数或已发放金额，不展示他人的收款资料或明细。
- 模板已包含月份选择、前三名、完整列表及“我的排名”。首版可默认本月，按自然月查询；接单榜使用有效完成时间。
- 并列名次、列表分页和无成绩展示由新对话实现统一规则并在页面说明，不伪造数据；历史月份应可随着实际退款和状态纠正反映有效结果。完成后被后台更正为未完成时，不再计入有效完成数量；重新有效完成也只算一单，沿用服务端有效完成日期。
- 后台角色拥有的其他权限不应导致手机排行接口返回额外客户、财务或账号秘密。

## 8. 自动更新、消息与通知

### 8.1 已确认的需求

- 网页打开时，订单和处理结果自动更新，不依赖用户反复刷新。
- 指定订单、退单处理是重点提醒；验收及提现结果按讨论建议纳入。
- 公共抢单池新单提醒可提供独立开关，默认关闭，避免所有人不断收到消息。
- 指定订单 5 分钟未接受，提醒客服处理。
- 用户希望关闭网页后也能收到提醒，接受添加到桌面并授权通知。
- 首版不接企业微信或普通微信自动消息，不要求打手进行额外平台身份绑定。

### 8.2 实施建议

- 可选择现有架构适合的短轮询、SSE 或 WebSocket；以真实后端事件和状态为准，断线重连后重新获取最新数据。
- 关键消息在服务端留有本人可见记录，浏览器推送只作为提醒入口；通知权限被拒绝时，仍可正常登录、处理订单及查看站内消息。
- 5 分钟任务由服务器按指派时间和当前状态判断，不能依赖某个用户一直打开页面。重新指派后旧计时失效，已接受或已拒绝不继续重复提醒。
- 通知应打开有权限的订单或处理详情；过期订单、换账号、退出登录时不越权显示或继续向旧绑定推送私人业务。
- 接口“接受发送”不等于用户已经收到、阅读或接单。后台可分别展示业务是否处理和发送异常，不把推送成功直接改成接单成功。

### 8.3 上线限制必须如实验证

网页关闭后的推送效果需要以中国大陆真实网络、安卓和苹果实际设备测试为准，不得宣称“所有手机必达”。苹果主屏幕 Web App 推送有系统版本、添加桌面和通知授权条件；不同安卓浏览器、网络及系统设置也会影响效果。

如果目标手机无法达到要求，应报告支持范围及失败场景，再由用户决定替代提醒方案或是否接受该上线限制；不能静默删掉离线提醒需求，也不能为此自行扩大首版到企业微信、短信或原生 App。
