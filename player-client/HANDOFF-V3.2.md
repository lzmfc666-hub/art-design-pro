## 发现的具体问题与修复

1. 历史扩展后，订单摘要可见不能等同私人详情授权。旧 claim/submit/return 成功后回到公共池，原 POST 同编号不得重返旧私人快照；现在返回403，原结果 GET 仍能只读确认，新轮次首次资格仍按原规则判断。
2. 历史材料所属的旧队友曾可凭附件 ID 读他人截图；关联授权增加当前负责人/队友条件，历史摘要不恢复图片权限。自有上传规则保留。
3. 打手传入 paidAt 日期筛选可通过真实 total 推断隐藏付款日；现在在过滤前拒绝403，空结果同样拒绝，后台原日期筛选保留。
4. 数值零页码曾被默认值吞掉；统一分页使用明确缺省判断，零、负数、超出页大小、非法日期及反向日期区间拒绝。
5. 原生 Web Locks 的排队回调曾在另一 renderer 存储标记传播前放行第二个意图。本轮改为不排队保留；暂未收到原标记时保持发送门禁，收到后仅恢复原编号。权限刷新及取消路径不会把未发送意图变成可查、可重试的新操作。
6. Lobby核对已确认但最新读取未完成时曾显示可点击，handler因busy提前返回；修正UI门禁并给验证裸等待加超时。320px历史摘要曾竖排，已修复并加入标题/返回链接几何断言，实际截图复查正常。

## 机制限制及上线条件

`not-recorded` 不能排除迟到提交，不能解锁新编号；只有原完整 body、原编号、原账号且当前允许重试时可显式重试。缺 body 的恢复标记只能只读核对或联系后台。结果查询中的重试建议反映账号/操作族开关，不能代替具体目标的权限和写事务最终裁决。

没有 Web Locks 时不保证跨标签原子首次提交，但每个未知编号仍分别保存、逐项确认，不相互覆盖；本地存储不可用时不保证重载恢复。有 Web Locks 的结论只覆盖本轮真实双标签验证，不能承诺所有浏览器跨进程调度的绝对原子性。保留者写标记前取消且无标记时，等待页保守保持限制，须重新加载核对，不猜测可以再次提交。

分页减少传输和页面渲染，底层目前仍解析 SQLite 中的完整业务 JSON，账本读取会构建本人完整流水后筛选分页；不称为实体表 SQL 分页或无限容量。请求并发不换算在线人数。本机结果不等同正式服务器容量。
